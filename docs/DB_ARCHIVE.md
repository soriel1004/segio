# 서버에서 결재 문서를 일괄 보관하기

관리자가 CentOS 서버에서 대상 직원 ID를 지정하면 `cell_000`의 개인 관계로 확인되는 문서·관련 기록과 첨부를 한 번에 수집하고, Windows에서 검색·열람할 HTML 보관함과 ZIP을 만듭니다. 웹 문서 페이지를 순회하지 않습니다. 이 경로에서는 직원 ID가 추출 대상이며 DB 접속은 서버의 기존 SEGIO 설정을 재사용합니다. **직원이 Windows에서 SEGIO ID·암호로 로그인해 관리자가 준비한 DB 보관본을 받으려면 [직원 로그인 안내](WINDOWS_LOGIN.md)를 보세요.**

운영 구조 보고서의 PostgreSQL 8.4.20·UTF8과 공개된 SEGIO 보조 소스를 기준으로 구현했습니다. 임시 PostgreSQL 16.2에서 합성 자료로 검증했으며 실제 CentOS 6/Python 2.6/PostgreSQL 8.4에서 추출한 운영 문서의 정확성은 아직 확인해야 합니다. 보관함이 생성되어도 계정 삭제 영향이 검증되는 것은 아닙니다.

## 실행

1. [최신 프로젝트 ZIP](https://github.com/soriel1004/segio/archive/refs/heads/main.zip)을 Windows에서 받아 압축을 풉니다. GitHub 화면을 셸 스크립트로 저장하지 않습니다.
2. ZIP 안의 **`tools` 폴더 전체**를 서버로 복사합니다. 최소 필요 파일은 `export_approval_db.py`, `export_schema_from_segio_config.py`, `approval_db_columns.json`, `db_archive_index.html`입니다.
3. `tools` 폴더가 보이는 상위 폴더에서 관리자로 실행합니다. `USER_ID`를 실제 퇴사자 ID로 바꿉니다. 추가 Python 패키지 설치나 PostgreSQL 설정 변경은 필요하지 않습니다.

```bash
python ./tools/export_approval_db.py --user USER_ID
```

기존 설정을 자동으로 찾지 못했으면 구조 보고서 생성 때 사용한 설정 파일 경로를 지정합니다. 암호를 명령에 넣지 않습니다.

```bash
python ./tools/export_approval_db.py --user USER_ID \
  --config /home/segio/cell000/etc/db.conf
```

기본 셀 경로는 지정한 `etc/db.conf`의 상위 셀 폴더입니다. 실제 `data` 폴더가 다른 곳이면 `--cell /실제/셀경로`로 명시합니다. 저장 위치는 현재 폴더이며 기존 자료를 덮어쓰지 않고 새 폴더와 ZIP을 만듭니다. 다른 위치에 저장하려면 이미 존재하는 디렉터리를 지정합니다.

```bash
python ./tools/export_approval_db.py --user USER_ID --output /backup
```

성공하면 두 경로가 출력됩니다.

```text
Saved archive ZIP: .../segio-USER_ID.zip
Saved summary: .../segio-db-USER_ID-임의값/export-summary.txt
```

ZIP 파일명에는 임의 영문·숫자를 붙이지 않습니다. 같은 이름의 파일이 있으면 `segio-USER_ID-2.zip`, `segio-USER_ID-3.zip`처럼 번호를 붙여 기존 백업을 보존합니다.

ZIP을 Windows로 옮겨 압축을 풀고 **`index.html`**을 Edge나 Chrome에서 엽니다. 검색해서 본문·결재선·첨부를 열 수 있습니다. 브라우저 인쇄에서 PDF로 저장할 수 있습니다. HTML 보관함을 사용하는 데 Python·Playwright·전용 Chromium 다운로드는 필요하지 않습니다. 사내 브라우저 정책이 로컬 HTML 열기를 막으면 기존 프로그램의 **보관함 열기**에서 압축을 푼 폴더를 선택할 수 있습니다.

결과 공유에는 **`export-summary.txt`만** 사용합니다. 이 파일에는 건수·범위·상태가 있으며 실제 본문·제목·암호는 없습니다. ZIP에는 실제 직원 문서와 첨부가 있으므로 Windows 보관 위치로 전송하여 관리합니다. `db.conf`나 ZIP을 진단 보고서로 올릴 필요는 없습니다.

실패하면 오류 문구를 확인합니다. 미완성 폴더와 ZIP은 오류 처리에서 지우며, 암호를 추측하거나 인증 설정을 바꾸지 않습니다. 갑작스러운 전원 종료나 `kill -9`로 중단한 경우에는 오류 처리와 임시 파일 정리가 실행되지 않을 수 있습니다.

## 수집 범위

| 관계 | 사용하는 구조 |
| --- | --- |
| 기안 | `approval_document.uid`와 과거 문서의 `uid` |
| 결재·합의·참조·대결 | 현재/백업 `approval_line.p_no`와 `uid`, `target_id` |
| 별도 참조·자동회람 | 소스에서 확인한 `UID@@이름`, `UID@@부서@@이름` 목록의 ID |
| 개인 수신·발송 참여 | `doc_recv_uid`, 현재/백업 `approval_send_box.doc_no`와 `doc_uid`, `recv_user`, `recv_uid` |
| 댓글·즐겨찾기·내부 저장 참여 | 현재/백업 댓글의 `doc_no`, 즐겨찾기의 `doc_no`, 내부 저장 기록의 `p_no` |
| 첨부 | 선택된 문서의 `approval_attach_info.doc_no`, `<셀>/data/approval/upload/<fpath>` |
| 결재자 이름·서명 | 저장된 결재선의 이름·직급·부서·상태·일시·서명 HTML, 관련 회원 표시 정보 |

ID는 정확히 일치해야 하며 `kim`을 찾기 위해 `kim2`를 포함하지 않습니다. 참조와 자동회람은 확인된 `@@` 구조를 가진 토큰만 해석하여 표시 이름 일부를 직원 ID로 취급하지 않습니다. 개인 관계로 선택된 문서 번호의 현재 문서와 남아 있는 과거 버전을 함께 보관합니다. 삭제 표시나 반려·진행 상태로 임의 제외하지 않습니다. 실제 문서 번호로 이름을 만들고 원래 제목은 화면·기록에 보존합니다.

단일 읽기 전용 SERIALIZABLE 트랜잭션에서 각 결과의 기대 행 수와 실제 추출 행 수를 대조합니다. PostgreSQL 8.4에서 제공하지 않는 JSON 함수 없이 UTF8 값을 CSV의 16진수 텍스트로 운반하여 줄바꿈·쉼표·따옴표·빈 문자열·SQL NULL을 구분합니다. JSON 원본 기록은 DB 텍스트 표현을 보존하며 SQL NULL은 JSON null입니다. 모든 컬럼을 무조건 내보내지 않고 확인된 컬럼을 명시하며 회원 정보의 전화번호·메일 주소 등 불필요한 항목은 제외합니다.

본문과 서명의 HTML은 스크립트·폼·외부 연결을 제거한 표시용 HTML로 재구성합니다. 확인된 로컬 본문 이미지와 `img_insert.php?mode=app_images&fname=...`, 첨부 미리보기는 로컬 파일에서 래스터 이미지를 읽어 내장합니다. 선택된 회원의 동적 서명은 `sign_path`가 확인 가능한 셀 데이터 경로일 때만 가져옵니다. 외부 이미지는 요청하지 않습니다. 지원하지 않는 이미지·서명 주소나 파일은 `issues.json`에 남깁니다. 원래 DB HTML은 `database.json`에 남아 있습니다.

첨부는 검증된 업로드 경로 안의 일반 파일만 읽습니다. 경로 이탈·범위 밖 심볼릭 링크·누락·복사 중 변경은 기록하고 해당 파일의 성공을 표시하지 않습니다. 복사본의 크기·SHA-256은 `manifest.json`에 기록하며 기존 프로그램의 **파일 무결성 검증** 또는 `python -m segio_archive verify 보관폴더`로 확인할 수 있습니다.

## 대조가 필요한 범위

- **부서 공용 수신함·보안 등급·기타 공유 권한**으로만 보이는 문서는 개인 ID 관계만으로 전체 범위를 확정할 수 없습니다. 현재 부서에 속했다는 이유로 과거 부서 문서 전체를 포함하지 않습니다.
- `approval_ext_info`, `approval_report*`, `approval_work*`의 별도 업무·확장 기록은 연결 규칙이 확인되지 않아 이번 추출에 포함하지 않습니다. 실제 사용하는 확장 양식의 표시 내용과 DB 본문이 같은지 확인해야 합니다.
- 과거 문서는 당시 문서 본문과 남아 있는 관련 이력을 보관합니다. 문서·결재선·댓글의 백업 버전을 동일 시점으로 연결하는 규칙은 아직 확인되지 않아 과거 페이지에는 관련 행의 백업 시각을 함께 표시합니다. 당시 첨부 목록이 별도로 남아 있지 않으므로 현재 연결된 첨부와 같다고 보장하지 않습니다.
- DB 스냅샷 이후 파일을 복사합니다. 복사 중 변경 검사는 수행하지만 DB와 파일이 같은 시점이라는 보장은 아닙니다. 실제 보관 작업은 변경이 적은 시간에 수행하고 대표 문서와 첨부를 대조해야 합니다.
- 원래 인쇄 페이지의 정확한 레이아웃, 직인·서명·회사 로고, 외부 이미지, 범위 밖 관련 문서의 원본은 추가 대조가 필요합니다. 저장된 HTML은 재구성한 열람본이며 전자서명의 암호학적 검증이나 서버 복구 기능을 제공하지 않습니다.
- 메일은 이 추출기의 수집 대상이 아닙니다. 현재 보고서는 결재 관계만 포함하므로 실제 메일 저장 구조를 추가 확인해야 합니다. 기존 웹 수집기의 메일 경로는 별도로 유지합니다.

따라서 결과 상태는 `collected_with_warnings`, `account_deletion_verified`는 `false`입니다. `issues.json`, 실제 화면의 각 결재함 건수, Windows 오프라인 열람 결과와 비교하고 복제 환경의 계정 삭제 영향 시험을 진행해야 합니다. 개인 보관함과 별도로 서버 전체 복구용 백업도 필요합니다.

## 문서를 열었을 때 글자가 깨지는 경우

운영 확인에서 본문은 `%26lt%3Bp%26gt...` 형태로 URL 인코딩된 HTML 엔터티이며, 서명은 `/9j/4AAQ...` 형태의 JPEG Base64로 저장된 사례가 확인됐습니다. 수정본은 표시할 때 확인된 HTML 인코딩을 제한된 횟수로 해제한 뒤 기존 HTML 정제를 적용하고, 래스터 이미지로 확인된 Base64 서명은 이미지로 내장합니다. 일반 HTML 안에 의도적으로 적은 엔터티·`+`·퍼센트 문자열은 그대로 보존합니다. `database.json`의 값은 저장 당시 원본이므로 인코딩된 문자열이 남아 있는 것이 정상입니다.

이 형식으로 이미 추출한 보관함은 원본으로 보관하고, 새 프로젝트 ZIP의 `tools` 파일들을 서버에 교체한 뒤 같은 ID로 다시 추출합니다. DB를 변경하지 않으며 새 보관함과 ZIP이 생성됩니다. 예를 들어 `/root/tools`에서 기존 대상 `koro`를 다시 추출합니다.

```bash
python ./export_approval_db.py --user koro
```

새 ZIP을 Windows에 풀고 **본문·결재선 보기**로 확인합니다. `export-summary.txt`에는 URL/엔터티 해제 횟수와 Base64 서명 표시 건수가 추가됩니다. 이 원인에 해당하는 경우 실제 문서나 진단 파일을 업로드할 필요는 없습니다.

먼저 **본문·결재선 보기**, **DB 기록**, 첨부 중 어디에서 발생하는지 구분합니다. 본문 위쪽의 고정 문구(예: `저장된 결재선 기록`)도 깨지는지, 문서 본문만 깨지는지에 따라 파일 인코딩과 저장된 본문 형식을 구분할 수 있습니다. `DB 기록`은 원래 DB 값을 보존한 JSON 데이터이며 문서의 인쇄 화면은 아닙니다.

기존 보관함을 그대로 읽는 `tools/diagnose_archive_text.py`로 파일 UTF-8 유효성, 인코딩 선언, 고정 한글 제목, 본문의 HTML·이스케이프·URL 인코딩 등의 형식 패턴을 집계합니다. 새 프로젝트 ZIP에서 이 도구를 서버에 복사하고, **ZIP을 만들 때 남아 있는 보관 폴더** 경로를 지정합니다. 아래 예시의 폴더 경로는 실제 생성된 경로로 바꿉니다.

```bash
python ./diagnose_archive_text.py /root/tools/segio-db-koro-0x_ImT
```

출력된 집계 JSON만 전달하면 됩니다. 도구는 파일을 수정하지 않으며 본문·제목·직원 ID·파일명·실제 경로·암호를 출력하지 않습니다. 이 패턴 집계만으로 특정 문자셋이 원인이라고 확정하지는 않습니다. 원인 확인 후 표시 처리를 조정하며 `database.json`의 원본 값은 보존합니다.
